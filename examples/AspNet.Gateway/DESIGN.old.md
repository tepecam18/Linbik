## Revision 2 — Token Taxonomy, Federation Topology, Library Roles

> Rev 1, birkaç eksik premise barındırıyordu. Rev 2, üç sorudan oluşan
> office-hours kararı sonrası şu eklemeleri/düzeltmeleri getirir:
>
> 1. **Self şeması** `Linbik.Core`'un `AddLinbikPasetoBearer`'ından
>    `Linbik.PasetoAuthManager`'ın `AddLinbikPasetoAuth` + `UseLinbikPasetoAuth`'una
>    swap edilir (login/callback/refresh/logout endpoint'leri gerçek hayatta zorunlu).
> 2. **`/apps` endpoint'leri her servisin kendi gateway'inde** yaşar; başka bir
>    servisin gateway'i Apps trafiğini proxy etmez. Cron/scheduler doğrudan hedef
>    servisin `/apps/...`'ına gider (`Linbik.YARP.UseLinbikS2S` + `IS2STokenProvider`
>    pattern'ı, ayrı outbound örneklerde gösterilir).

### Token Taxonomy (canonical)

| Scheme | Anlam | Token üretici | Token tüketici | İlgili Linbik paketi |
|---|---|---|---|---|
| **Self** | Bu uygulamanın kendi kullanıcısı (cookie tabanlı login) | Host uygulama (kendi sunucusunda, Linbik platformuyla OAuth code exchange sonrası yerel olarak yeniden imzalanır) | Host'un kendi `/self/**` endpoint'leri | `Linbik.PasetoAuthManager` / `Linbik.JwtAuthManager` |
| **Delegated** | Başka bir uygulama, bir kullanıcı adına (on-behalf-of) | **Linbik platformu** | Host'un `/delegated/**` endpoint'leri ve gerideki microservice'lerde `[LinbikDelegatedAuthorize]` | `Linbik.Core.AddLinbikPasetoBearer` (gateway doğrulama) + `Linbik.Server` (downstream) |
| **Apps** | Başka bir uygulama, kendi adına (S2S / client_credentials) | **Linbik platformu** | Host'un `/apps/**` endpoint'leri ve gerideki microservice'lerde `[LinbikApplicationAuthorize]` | `Linbik.Core.AddLinbikPasetoBearer` (RequireApplicationToken=true) + `Linbik.Server` |

Net ayrım: **Self'i host üretir; Delegated ve Apps'ı Linbik platformu üretir.**
Gateway her üçünü de **sadece doğrular**, ama Self için `PasetoAuthManager` ek olarak
login/callback/refresh/logout endpoint'lerini ve cookie yönetimini sağlar.

Kaynak referans: kullanıcının senaryo özeti — "self için sadece kullanıcı var,
delegated için kullanıcının bir uygulama üzerinde yaptığı işlemler var, apps için
uygulamanın kendisi için işlemler var olması gerekiyor."

### Library Roles (netleştirildi)

| Paket | Konumu | Sorumluluğu |
|---|---|---|
| `Linbik.PasetoAuthManager` | Bu sample (Self şeması) | Login/callback/refresh/logout endpoint'leri, Linbik platformuyla OAuth code exchange, yerel PASETO yeniden imzalama, cookie yönetimi (`authToken`, `integration_{pkg}`) |
| `Linbik.Core` | Bu sample (Delegated + Apps) | `AddLinbikPasetoBearer` ile sadece doğrulama. Multi-scheme named options (PostConfigure pattern). |
| `Linbik.YARP` | **Bu sample'da kullanılmaz** | Outbound senaryolar için (host → downstream, `integration_{pkg}` cookie → Authorization Bearer inject, `IS2SServiceClient`). Inbound gateway için ham YARP + yerel claim transform yeterli. |
| `Linbik.Server` | Downstream microservice (gateway'in arkasında) | `[LinbikDelegatedAuthorize]`, `[LinbikApplicationAuthorize]`, `Linbik-*` okuma extension'ları, integration lifecycle, telemetry. **Sample'ın `Downstream.Sample`'ı şimdilik kullanmıyor** (basitlik için header okuma); gerçek üretim downstream'i `Linbik.Server` kullanır. |
| `Linbik.JwtAuthManager` | Alternatif Self (PASETO yerine JWT) | Aynı endpoint setini RS256 JWT ile sağlar. Sample tek altyapı (PASETO) gösterir — ikisi birlikte kullanılmaz. |

### Apps Placement Karar Notu

**Karar: A — Apps her servisin kendi gateway'inde, cross-service Apps proxy YOK.**

Bir tüketici servis (cron, scheduler, başka bir microservice) hedef servisten
Apps endpoint'i çağırmak istediğinde:

```
Consumer.Cron  ──(IS2STokenProvider'dan apps token al)──▶  api.target.com/apps/...
```

Doğrudan. Tüketicinin kendi gateway'inden geçmez. Çünkü:
- Apps token Linbik platformunda üretilir, hedef servis tarafından doğrulanır — tek hop.
- `Linbik.YARP.UseLinbikS2S()` + `IS2STokenProvider` zaten bu pattern'ı destekliyor (token caching + auto-refresh).
- İki katmanlı auth ve token translation complexity'sini ortadan kaldırır.

**Reddedilen B (cross-service proxy)**: merkezi audit/governance gerçekten gerekirse
ayrı bir sample konusu ("mesh gateway" varyantı), scope dışı.

### Authorize vs Anonymous Strategy

**Default: deny.** Hiçbir policy'ye girmemiş endpoint 401 döner.

Üç mekanizma:

1. **YARP route metadata'sı**: `"AuthorizationPolicy": "SelfPolicy"` zorunlu kılar.
   `"AuthorizationPolicy": "Anonymous"` (yerleşik YARP policy adı) auth atlar.
2. **Gateway'in iç endpoint'leri** (PasetoAuthManager'ın `/api/linbik/*`'ı, `/openapi/*`,
   `/scalar/*`, `/health`): explicit `.AllowAnonymous()`.
3. **Fallback policy**: `AddAuthorizationBuilder().SetFallbackPolicy(RequireAuthenticated)`
   ile herhangi bir endpoint policy belirtmediyse default reddedilir.

Örnek `appsettings.json` route'ları:

```json
{
  "Routes": {
    "self-orders":      { "AuthorizationPolicy": "SelfPolicy",      "Match": { "Path": "/self/orders/{**c}" } },
    "delegated-search": { "AuthorizationPolicy": "DelegatedPolicy", "Match": { "Path": "/delegated/search/{**c}" } },
    "apps-reports":     { "AuthorizationPolicy": "AppsPolicy",      "Match": { "Path": "/apps/reports/{**c}" } },
    "public-status":    { "AuthorizationPolicy": "Anonymous",       "Match": { "Path": "/public/status" } }
  }
}
```

## Problem Statement

`examples/AspNet.Gateway/` altında, **.NET 10** ile Linbik'i bir API gateway olarak
kullanmanın referans örneği olacak bir proje istiyoruz. Senaryo:

- Auth tek noktada (gateway). Downstream mikro servislerde `[Authorize]` yok.
- Her gelen istekte gateway, JWT'yi parse eder, allowlist'teki claim'leri
  `Linbik-*` header'larına yazar ve downstream'e iletir.
- Gelen istekte zaten var olan `Linbik-*` header'ları **önce silinir** ki
  dışarıdan spoof edilemesin.
- Linbik servisleri yalnızca **Self** modunda. Ekstra entegrasyon servisi
  kullanmak isteyen tüketiciler için **Delegated** ve **Apps** katmanları da olur.
- Üç scheme: `LinbikAuthorize` (Self), `LinbikDelegatedAuthorize` (Delegated),
  `LinbikApplicationAuthorize` (Apps) — Linbik.Core'da hazır.
- OpenAPI dokümanları gateway'de toplanır. Self/Delegated/Apps üç ayrı doküman.
  Self prod'da kapalı, diğer ikisi açık (default).
- Gateway kullanıldığında Linbik.YARP'taki yönlendirme görevi gateway'e taşınır.

## What Makes This Cool

Linbik'in bugünkü kütüphane setine "edge gateway" pattern'ını net biçimde gösteren
bir referans yok. Mikro servisleri auth'tan tamamen arındırıp gateway'i tek
otorite yapmak; downstream'lerin kod tarafında `User.Claims` yerine `Request.Headers`
okuması; OpenAPI'yi audience'a göre üç gruba ayırıp prod'da Self'i kapatmak —
bunların hepsi tek bir runnable örnekte birleşince Linbik'in nasıl
"production-ready gateway" olarak konumlandığı görünür hale geliyor.

## Constraints

- .NET 10. `Microsoft.AspNetCore.OpenApi` (Swashbuckle değil).
- Tüm 3 scheme **PASETO v4.public (Ed25519)** kullanır — JWT yok.
- **Self** şeması `Linbik.PasetoAuthManager`'ın `AddLinbikPasetoAuth` +
  `UseLinbikPasetoAuth`'unu kullanır (login/callback/refresh/logout endpoint'leri
  dahil). **Delegated** ve **Apps** şemaları `Linbik.Core`'un
  `AddLinbikPasetoBearer`'ı ile sadece doğrulama yapar. _(Rev 1'de tümü Core idi;
  Self login endpoint'i eksikti — Rev 2'de swap.)_
- Linbik.JwtAuthManager **kullanılmaz** (PASETO ile karşılığı PasetoAuthManager).
- **Linbik.YARP bu sample'da kullanılmaz** — Linbik.YARP outbound (host → downstream,
  integration cookie inject) için tasarlanmış; bu sample inbound claim extraction
  yapan bir gateway örneği, ham YARP + yerel transform yeterli.
- Sample bir paket çıkarmaz; gateway parçaları sample içinde yerel sınıflar.

## Premises (onaylandı)

1. **Gateway = tek auth çıtası.** Downstream `[Authorize]` çalıştırmaz, sadece
   `Linbik-*` header'larına bakar. Header spoof'a karşı koruma: **network
   izolasyonu varsayımı** (downstream sadece gateway'in erişebileceği ağda).
   _Risk_: gateway bypass edilirse downstream spoof'a açık. Üretim notu doc'a girer.
2. **Allowlist + `Linbik-*` prefix.** Tüm prefix gelen istekte silinir, sonra
   JWT parse'tan sonra allowlist'teki claim'ler yeniden yazılır.
3. **Endpoint ayrımı route prefix ile.** `/self/**` → LinbikScheme,
   `/delegated/**` → LinbikDelegated, `/apps/**` → LinbikApplication.
4. **OpenAPI N:N üyelik.** Bir endpoint birden fazla dokümanda görünebilir
   (örn. hem Self hem Delegated). Üyelik kaynağı: downstream operation'da
   `Linbik-audiences` extension varsa o, yoksa cluster metadata'sındaki
   default audience.
5. **Linbik.YARP yerine** ham YARP + yerel inbound transform. Linbik.YARP
   outbound senaryosu için tasarlanmış (host → downstream, integration cookie
   → Authorization Bearer); bu sample inbound gateway gösterir.
6. **Sample sadece sample.** Linbik.Gateway paketi şimdi çıkmıyor.

## Approaches Considered

### Approach A — YARP + inline gateway pipeline (chosen)
Sample içinde 3 scheme + 3 policy, YARP route config (appsettings), tek
inbound transform sınıfı (header sanitize + claim injection), 3 OpenAPI
dokümanı + downstream aggregator.

### Approach B — `IHttpForwarder` + elden routing
YARP soyutlamasını atla, `app.Map` ile elden forward. Edge case (streaming,
WS, header forward) yükü artar.

### Approach C — Şimdi `Linbik.Gateway` paketi çıkar
Premature abstraction riski. Pattern olgunlaşmadan paketleme.

### Auth Pipeline (Gateway)

`GatewayAuthenticationExtensions.AddLinbikGatewayAuthentication(...)`:

Üç scheme de **PASETO v4.public (Ed25519)** kullanır. `Linbik.Core`'da
`PasetoHelperService : IPasetoHelper` (`Paseto.Core` NuGet, Ed25519 / v4.public)
zaten hazır.

Gateway'e özgü `PasetoAuthenticationHandler : AuthenticationHandler<PasetoAuthenticationOptions>`
yazılır. Seçenekler:

| Scheme | Token kaynağı | Public key kaynağı | Beklenen claim'ler |
|---|---|---|---|
| **LinbikScheme** (Self) | `authToken` cookie | `appsettings Linbik:Gateway:SelfPublicKey` | `sub`, `name`, `preferred_username` |
| **LinbikDelegated** | `Authorization: Bearer` | `appsettings Linbik:Gateway:DelegatedPublicKey` | `sub`, `name`, `preferred_username`, `azp` |
| **LinbikApplication** | `Authorization: Bearer` | `appsettings Linbik:Gateway:AppsPublicKey` | `source_service_id`, `source_package`, `target_package`, `role` |

`PasetoAuthenticationOptions` alanları: `PublicKeyBase64`, `TokenSource` (Cookie|Bearer),
`CookieName`, `ExpectedAudience`, `SchemeLabel`.

Handler akışı:
1. Token'ı oku (cookie veya Bearer header).
2. `IPasetoHelper.ValidateTokenAsync(token, publicKey, audience)` çağır.
3. Geçerliyse `IPasetoHelper.GetTokenClaims(token)` ile claim dict'i al.
4. `ClaimsPrincipal` oluştur, `AuthenticateResult.Success(ticket)` döndür.
5. Geçersizse `AuthenticateResult.Fail(...)`.

Üç policy: `SelfPolicy`, `DelegatedPolicy`, `AppsPolicy` — her biri tek scheme
zorunlu kılar (`RequireAuthenticatedUser` + `AddAuthenticationSchemes`).

> Not: 3 scheme'i route prefix'inden seçmek için YARP'ın `AuthorizationPolicy`
> route property'si kullanılır. Her route appsettings'te
> `"AuthorizationPolicy": "SelfPolicy"` belirtir.

### Header Sanitize + Claim Injection

`ClaimToHeaderTransform : IRequestTransform`. İki adım:

1. **Sanitize.** Gelen istekteki `LinbikGatewayDefaults.HeaderPrefix` (`Linbik-`)
   ile başlayan tüm header'ları proxy isteğinden sil. Authorization header da
   düşer (downstream'in JWT görmesine gerek yok).
2. **Inject.** `HttpContext.User.Claims` üzerinden allowlist:

| Claim | Header |
|---|---|
| `sub` | `Linbik-Sub` |
| `name` | `Linbik-Name` |
| `preferred_username` | `Linbik-Username` |
| `azp` | `Linbik-Azp` |
| `scope` | `Linbik-Scope` |
| `role`/`roles` | `Linbik-Roles` (virgüllü) |
| `source_service_id` | `Linbik-Source-Service` |
| `source_package` | `Linbik-Source-Package` |
| `target_package` | `Linbik-Target-Package` |
| `aud` | `Linbik-Audience` |

Ek olarak meta:
- `Linbik-Scheme`: hangi scheme ile doğrulandı (self|delegated|apps)
- `Linbik-Gateway`: bu gateway'in adı (audit)

Allowlist `LinbikGatewayDefaults` içinde `static readonly` dict. Genişletme
gereken müşteriler `appsettings.json`'da `LinbikGateway:ClaimHeaderMap` ile
override edebilir.

Program.cs (özet):

```csharp
builder.Services.AddLinbik(...)
    .AddLinbikJwtAuth(builder.Configuration.GetSection("Linbik:JwtAuth"));
builder.Services.AddLinbikGatewayAuthentication(builder.Configuration);
builder.Services.AddReverseProxy()
    .LoadFromConfig(builder.Configuration.GetSection("ReverseProxy"))
    .AddTransforms(b => b.RequestTransforms.Add(new ClaimToHeaderTransform()));

var app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();
app.MapLinbikOpenApiAggregator();
app.MapReverseProxy();
```

### OpenAPI Aggregation (3 doküman, N:N endpoint üyeliği)

.NET 10'da `Microsoft.AspNetCore.OpenApi` paketi yerleşik. Gateway 3 doküman
serve eder:

- `GET /openapi/self.json`
- `GET /openapi/delegated.json`
- `GET /openapi/apps.json`

`OpenApiAggregator` periyodik (veya on-demand cache, 60sn TTL) downstream'lerin
`/openapi/v1.json`'unu çeker. Cluster konfigürasyonu hangi downstream'in hangi
URL'sini sorgulayacağını bilir (cluster metadata `linbik:openapi-path`,
default `/openapi/v1.json`).

**Audience eşlemesi (N:N için kritik):**

Her downstream operation'ı için sıralı karar:
1. Operation'da `Linbik-audiences: [self, delegated]` extension varsa → onu kullan.
2. Yoksa → route metadata'sındaki `linbik:audiences` (virgüllü liste) → onu kullan.
3. Yoksa → route prefix'inden türet (`/self/*` → `[self]`, vs).

Bu sırayla operation hangi doküman(lar)a girer kararlaştırılır. Bir endpoint
hem `[self, delegated]` listesinde ise iki dokümana da yazılır (path rewrite
ile: `self.json`'da `/self/...`, `delegated.json`'da `/delegated/...`).

`AudienceFilter` aggregator içinde, her operasyon için bu kararı uygular ve
çıktı dokümanına filtreleyerek koyar.

**Default visibility:**

- `IWebHostEnvironment.IsProduction()` ise `/openapi/self.json` 404 döner.
- `appsettings.json` üzerinden override:

```json
"LinbikGateway": {
  "OpenApi": {
    "Self":      { "ExposeInProduction": false },
    "Delegated": { "ExposeInProduction": true },
    "Apps":      { "ExposeInProduction": true }
  }
}
```

UI: `Scalar.AspNetCore` (sadece UI için)
3 ayrı sayfa. Sample'da `Scalar` tercih edilir; .NET 10 OpenAPI ile native uyumlu.

### Downstream.Sample

Auth yok. `[Authorize]` yok. Tek bir controller `EchoController` `Request.Headers`
üzerinden `Linbik-Sub`, `Linbik-Scope` vs. okur ve döner. Bu ile downstream
servisin gateway'e nasıl güvenip header okuduğu örneklenir. Ayrıca downstream
kendi `openapi.json`'unu yayınlar; operation'lara `Linbik-audiences` extension
örneği eklenir (OpenAPI document transformer).

## Open Questions

1. **OpenAPI cache TTL ne olmalı?** 60sn şimdilik, prod'da config'le ayarlanır.
2. **Downstream openapi.json'a nasıl ulaşacağız üretimde?** Cluster destination
   URL + relative path varsayımı şimdilik yeterli. Service discovery konusu sample
   kapsamı dışı.
3. **Refresh token akışı gateway'de mi olacak?** Şu an out-of-scope; Self için
   cookie zaten Linbik.JwtAuthManager tarafından yönetiliyor.
4. **Rate limit gateway'de mi?** `Linbik.JwtAuthManager.RateLimitExtensions`
   mevcut; sample'a opsiyonel bir kayıt eklenir (kapalı, README'de "açmak için"
   notu).

## Success Criteria

- `dotnet run` ile gateway 5100, downstream 5101'de ayağa kalkar.
- `curl` ile cookie auth → `/self/echo/hello` → downstream `Linbik-Sub` görür,
  döner.
- Bearer token ile `/delegated/...` → `Linbik-Username` downstream'de görünür.
- S2S token ile `/apps/...` → `Linbik-Source-Package` downstream'de görünür.
- Gelen istekteki manipüle `Linbik-Sub: attacker` → downstream'de **görünmez**
  (gateway silmiş, yenisini yazmış).
- `/openapi/self.json`, `/openapi/delegated.json`, `/openapi/apps.json` ayrı
  içerik döner. `Linbik-audiences: [self, delegated]` olan bir downstream
  endpoint'i hem `self.json`'da hem `delegated.json`'da görünür.
- `ASPNETCORE_ENVIRONMENT=Production` ile `/openapi/self.json` 404, diğer ikisi
  200.
- README adım adım manuel test komutlarını içerir.

## Production Notes (sample kapsamı dışı ama README'ye not)

- **Header spoof riski**: Downstream'ler **sadece** gateway erişiminde olacak
  şekilde ağ izolasyonu (private VNet, internal LB, mTLS, K8s NetworkPolicy).
  Aksi halde saldırgan downstream'i doğrudan çağırıp `Linbik-Sub`'u spoof'lar.
- **Üretime geçerken** gateway → downstream arası kısa ömürlü HMAC imzalı
  internal JWT eklenmesi şiddetle önerilir (header'lara ek olarak `Linbik-Sig`
  ile claim'lerin bütünlüğü doğrulanır). Bu, ileri sürüm Linbik.Gateway
  paketinin core değeri olabilir.
- **Self prod'da kapalı** OpenAPI default'u: dahili API'nin attack surface'ini
  azaltır.

## Reviewer Concerns

Adversarial review bu environment'ta otomatik koşturulamadı (gstack subagent
araçları Unix-only). Manuel kontrol noktaları:

- **N:N OpenAPI birleştirme** path collision yapabilir: aynı path iki dokümanda
  farklı prefix ile (`/self/payments/x` vs `/delegated/payments/x`) — aggregator
  prefix'i route'a göre yeniden yazmalı.
- **Allowlist'in genişletilmesi** appsettings'ten override edildiğinde validator
  unutulmamalı (yanlış case'li header isimleri sessizce düşer).
- **YARP `AuthorizationPolicy` ile birden fazla policy** birleştirilemez; bir
  endpoint sadece tek policy alabilir. Bir endpoint hem self hem delegated
  doküman üyeliği OpenAPI seviyesinde mümkün ama **runtime'da iki ayrı route**
  ile (her biri kendi policy'sini taşıyarak) ifade edilmeli — bu noktayı README
  ve sample açıkça göstermeli.

## What I noticed about how you think

- "bazı endpointler birden fazla dokümanda bulunabilecek" — N:N üyeliği baştan
  fark etmek, çoğu kişinin OpenAPI aggregator'a başladıktan sonra gördüğü bir
  şey. Bu detay gateway'in en kritik tasarım kararını şekillendirdi.
- "self prod ortamda kapalı diğerleri açık olmalı" — attack surface bilinciyle
  default seçiyorsunuz. Sample'ı doğrudan üretim default'larıyla göstermek
  pattern'in benimsenmesini kolaylaştıracak.
- Header spoof'a karşı en hızlı yolu (network izolasyonu) seçtiniz, ama soruyu
  duyduğunuzda risk hemen netti. Sample bu trade-off'u README'de açıkça
  yazdığında, paket sürümünde HMAC internal JWT katmanı doğal sonraki adım
  olarak görünür.
